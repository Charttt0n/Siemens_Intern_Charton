## 二 驱动与存储实现

### UART 接收中断与缓冲区

UART0 接收使用外部 IRQ 0。中断处理函数读取硬件 DATA 寄存器并将字节写入环形队列，主循环从软件队列取出数据。128 字节数组保留一个空槽区分空和满，因此有效容量为 127 字节。队列满时保留原有数据、丢弃新字节，并记录丢弃数量。

实现中先清除本次 RX 中断标志，再读取 DATA，避免读取后新字节到达时被误清中断。发送仍采用有次数上限的轮询方式，尚未启用 TX 中断。测试在暂停前台消费时经真实 QEMU 串口发送 200 个不同字节，验证接收 200、保留前 127、丢弃 73，恢复后仍能正常收发。

### 分区与模拟 Flash

AN500 当前代码和数据区使用 SRAM，因此我将 NOR Flash 的操作规则放在存储接口中模拟，并将跨进程保存交给宿主机检查点工具。存储总长为 1 MiB，分区如下。

| 分区 | 大小 | 用途和访问限制 |
|---|---|---|
| Bootloader 预留区 | 64 KiB | 逻辑预留区域，API 禁止编程和擦除 |
| 主应用区 | 448 KiB | 保存镜像头及应用内容 |
| 备份固件区 | 448 KiB | 保留可读写空间，尚未实现自动恢复 |
| 参数区 | 64 KiB | 保存实验标记和后续配置数据 |

编程偏移与长度按 4 字节对齐，擦除按 4 KiB 对齐；编程只允许位从 1 变为 0，擦除后恢复为 0xff。接口拒绝越界、跨分区、非法对齐、Bootloader 区写入和缓冲区与存储重叠。整个写入请求先检查再执行，避免参数错误留下部分修改。

保存时，宿主机等待命令完成，暂停 QEMU，将存储区导出为镜像文件，再通过临时文件替换已有检查点。测试已验证保存后重启恢复、擦除结果保存、并发使用同一镜像被拒绝，以及替换失败时旧镜像保留。

这种机制只提供显式检查点持久化。强制终止 QEMU 后，上次保存之后的修改会丢失；它还不能作为真实 Flash 抗掉电恢复方案。

## 三 固件校验与应用交接

### 先确定镜像与地址约定

新增 32 字节小端镜像头，记录格式标识、格式版本、头长度、应用长度、固定加载地址、固件版本、内容 CRC32 和头 CRC32。Bootloader 先检查头和长度，再读取内容计算 CRC，随后检查栈顶、Thumb 入口与完整向量表。CRC 用于检测数据损坏，不提供签名认证或防回滚保证。

Bootloader 运行代码位于 0x00000000，应用代码加载到 0x00010000。二者的运行 RAM 分开：Bootloader 使用 0x20000000 至 0x20010000，应用使用 0x20010000 至 0x20200000；模拟存储位于 0x20300000 至 0x20400000。应用镜像从存储槽复制到运行区后，还要再次计算 CRC，防止加载过程中出现错误。

### 将处理器状态交给应用

跳转前关闭 UART、SysTick 和外部中断，清除挂起状态，设置应用 VTOR，再由汇编切换 MSP 和分支到应用复位入口。修改 MSP 后不再访问原 C 栈。应用自行完成数据初始化，确认交接状态后开启中断，并通过一次 SVC 调用验证应用向量表和异常返回。

```text
BOOT: stage4 image validation
IMAGE: CRC32 PASS
LOAD: verified at 0x00010000
JUMP: application
APP: CRT PASS
APP: HANDOFF PASS
APP: SVC PASS
APP: RUNNING
```

以上内容来自本次真实 UART 日志。QEMU 只直接加载 Bootloader ELF，应用由 Bootloader 从镜像中复制并启动；因此应用输出能够用于验证实际加载与交接链路。

### 验证方法与定位经验

第四阶段共通过 23 项检查，涵盖正常和最大长度镜像、空白镜像、错误格式、头和内容 CRC 损坏、超长内容、错误加载地址、非法 MSP 和入口、无效中断向量及加载后数据损坏。CRC 实现还在地址与未定义行为检查器下，与 Python zlib 的独立结果比较。

交接测试先让 CPU 实际执行中断屏蔽指令，再注入 NVIC、SysTick 和 PendSV 挂起状态。早期测试直接用 GDB 写 PRIMASK，但本机模型未按预期改变状态，导致注入的异常提前触发；改为执行指令并读回状态后，测试通过。这说明故障注入本身也需要验证，不能只看调试命令是否返回成功。
