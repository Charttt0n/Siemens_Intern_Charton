# 第二周实习周报：最小 Bootloader 启动与 UART

整理日期：2026-10-14。本报告按第二周任务范围整理本次实际实现与测试，不虚构五天工作经历。

## 本阶段完成情况

在第一周裸机 demo 的基础上，新增独立的 `bootloader.elf`：包含 48 项向量表、汇编段初始化、板级 VTOR 设置、固定时钟信息、CMSDK UART0 轮询发送，以及 C 环境自检。第一周目标保留，便于对照和回归。

第二周运行不再依靠 semihosting 打印，UART 启动日志经过寄存器访问实际输出到 QEMU 串口后端。源码、运行入口、自动验收脚本、架构笔记和测试记录均已整理。

## 我的实现思路

我首先区分了“程序能打印”与“串口驱动已工作”。第一周的 semihosting 输出只能证明工具链和基础 C 环境可用，所以这次把关闭 semihosting 作为验收条件，并检查最终反汇编没有 BKPT。

架构上，我把工作拆成启动层、板级层、UART 驱动层和主流程。启动层只处理进入 C 之前必须完成的内容；板级层提供当前模型的时钟信息；驱动层负责寄存器与错误返回；主流程组织自检和日志。这样后续增加串口接收时，主要修改驱动，不必重新改段初始化循环。

时钟部分不能照搬其他 MCU 的 PLL 初始化。除了看 QEMU 实现，我还查询了本机模型，确认 CPU 与 UART 使用 25 MHz。最终采用固定频率接口和 UART 分频配置。这个选择满足当前仿真的启动需要，但不等于已经掌握或实现真实硬件的晶振切换，文档中保留了这个差异。

## 测试如何支持结论

最终套件 12 项检查全部通过，其中包括 9 个第二周固件运行场景。三次正常启动各输出 144 字节，脚本逐字节比对完整内容，避免只看到开头的 BOOT 就认为成功。

对初始化，我在复位时把 20 字节 data 和 36 字节 BSS 主动写坏，再停到 main 检查。data 恢复预期初值、BSS 全零，而且段末哨兵没有被覆盖。这比依赖 QEMU 初始 RAM 恰好为零更能说明清零循环确实执行了。

对错误路径，我分别破坏 data 数组末项和 BSS 数组末项，固件都记录运行时错误并输出 FAIL；禁用 UART 后，固件通过状态变量报告错误；注入 UDF 指令后，异常处理记录了 HardFault 的异常号 3。这让我能区分数据检查失败、串口故障和处理器异常，而不是只面对一个没有输出的窗口。

另做了无效波特率、零时钟、空字符串指针等参数验证。错误配置被拒绝，而且不会破坏已有串口配置。完整步骤与原始证据见 [测试报告](../../codes/docs/week2-test-report.md)。

## 我特别记录的两个细节

一个是 PC 与向量表入口值不同。此次 Reset_Handler 位于 `0xc0`，向量项为 `0xc1`，最低位用于表示 Thumb 状态；调试记录必须区分实际 PC 与向量原值。

另一个是体积统计。size 显示 bss 为 4132 字节，但其中 4096 字节是显式保留的栈，真正 `.bss` 只有 36 字节。如果只把汇总数字抄进报告，会误判静态变量占用。

## 当前不足与下一阶段安排

目前 UART 是 TX 轮询模式，等待上限只是循环次数，尚未验证持续背压。异常处理只记录并停止，尚无恢复能力。代码区仍是模拟 SRAM，不能作为已实现的 Flash 使用。

第三周应先增加 UART 接收和中断测试，明确缓冲区溢出处理；同时单独设计 Flash 仿真存储层，区分“读写一个 RAM 数组”和“具备擦写约束及重启后保存”的存储行为。第二周留下的模块边界、状态变量和测试入口将用于后续扩展。
