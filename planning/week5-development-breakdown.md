# Week 5 代码开发拆解

日期：2026-10-31。本文是开发方案，不代表功能已实现或测试已通过。

依据：原规划书《Industrial Embedded Systems Bootloader Development》第 5 页，以及当前 codes 工程。原计划要求 Ymodem 接收、主备升级、参数区状态记录，以及 QEMU 全流程成功/失败验证。SHA256/RSA、运行故障自动回退、看门狗和完整配置接口属于 Week 6。

## 目标与关键设计

最终演示：旧应用 v1 能启动 → 主机发送 v2 升级包 → Bootloader 写入非活动槽 → 校验完整镜像 → 持久提交活动槽 → 重启并运行 v2。

核心约束：新镜像未完整验证和提交前，不擦除旧活动槽，也不改变启动选择。升级中断后仍能启动旧版本；提交完成后重启选择新版本。

建议采用逻辑 A/B 槽切换。FLASH_APP 与 FLASH_BACKUP 的物理地址不变，主备职责由 active_slot 决定。两槽都存放链接到同一执行地址 0x00010000 的应用，Bootloader 从选中槽复制到该地址后交接；不直接跳到备份槽的存储地址。下次升级写入另一个非活动槽。

## 按依赖执行的八个步骤

### 1. 建立 Week 5 入口与升级包契约

建议新增 codes/src/week5/main.c、codes/scripts/build-week5.sh、pack-week5.py，并在 codes/CMakeLists.txt 中增加 bootloader-week5.elf 目标。

- 保留原有四周构建目标与测试入口。
- 生成可区分输出的应用 v1/v2，使日志能证明启动的是新程序；只修改镜像头版本号不能证明应用已更新。
- 升级包明确为「32 字节现有镜像头 + 应用 payload」。不发送整块 1 MiB Flash，也不把 ELF 当成升级包。
- 区分协议声明的文件长度、头部声明的 payload 长度以及分区容量；要求文件长度恰好等于 32 + payload 长度，拒绝截断、额外尾部和越界。
- 定义进入升级模式的命令或启动等待窗口；无升级请求时能启动现有应用。

验收：Week 5 独立构建通过；v1/v2 升级包可离线解析，长度、版本和 CRC32 正确。

### 2. 让镜像校验与加载支持指定槽

建议在 image.c/image.h 中增加 image_validate_slot(dev, slot, info)、image_load_slot(dev, slot, info)；原 image_validate/image_load 继续包装 FLASH_APP，维持 Week 4 行为。

- 将头部读取、payload CRC、向量读取和复制中的固定 FLASH_APP 改为经过校验的 slot 参数。
- 只允许两个固件槽，拒绝 FLASH_BOOT、FLASH_PARAMS 和无效编号。
- 存储地址随 slot 改变，执行地址、RAM 边界和交接契约保持一致。
- 每次启动都重新校验所选镜像；参数区的“成功”标记不能替代镜像校验。

验收：分别把合法镜像放到两槽，均可校验、加载和运行；非法槽、坏镜像被拒绝；Week 4 回归通过。

### 3. 实现可恢复的升级元数据

建议新增 codes/src/week5/boot_meta.c、boot_meta.h。

记录字段建议：magic、格式版本、递增序号、active_slot、target_slot、升级状态、期望字节数、已完成字节数、候选镜像版本、错误码、记录 CRC、提交标记。

- 在 FLASH_PARAMS 中使用两个独立擦除页交替保存记录；已有擦除粒度为 4 KiB、编程粒度为 4 字节。
- 每次更新只擦除非当前有效记录所在页，写正文和 CRC，读回验证后最后写提交标记；不能先删掉唯一有效记录。
- 启动时检查提交标记、CRC、字段范围和序号，选取最新有效记录；明确序号回绕策略。
- 中断导致新记录无效时继续使用旧记录。活动槽改变必须通过完整提交，而非原地覆盖某个字节。
- 空白参数区提供明确的首次初始化策略；双记录均损坏时进入可重新升级的恢复入口，不能随意相信无效槽号。
- 进度按块或阶段记录；第一版中断后重新上传即可，不承诺断点续传。进度只表示已完成且可验证的写入。

验收：在擦除、正文写入、CRC 写入、提交标记写入的各阶段注入中断，重新读取都只能得到旧有效记录或新有效记录。

### 4. 实现 Ymodem 接收模块

建议新增 codes/src/week5/ymodem.c、ymodem.h、crc16.c、crc16.h，以及可替换的串口收发/计时适配层。采用开源实现时记录来源、固定修订和许可证，协议层与板级驱动分离。

- 先把文件接收到内存或测试 sink，协议逻辑通过后再连接 Flash。
- 明确本周支持单文件升级，支持约定的 Ymodem 数据块形式、首包元数据和传输结束交互。
- 检查包序号、反码、CRC16、文件长度和取消信号；实现超时、有限重试、重复包确认以及序号回绕。
- 重传的上一包只再次确认，不重复推进文件偏移；合法回绕不能被当作文件首包。
- 只将声明文件长度以内的有效字节交给写入层，协议末包填充不属于镜像内容。
- 传输期间同一 UART 不混入调试文本；日志通过独立通道或会话结束后输出。
- 计时使用实际单调时间基础，不能用未经校准的循环次数冒充毫秒。明确 RX 丢包、硬件 overrun、TX 超时的终止行为。

验收：正常发送、坏包重传、丢 ACK 后重复包、序号回绕、取消、超时、超长首包和末包填充均有可重复测试；至少用一个独立主机实现做互操作验证。

### 5. 接入非活动槽写入

建议新增 codes/src/week5/update.c、update.h，暴露 begin/write/finish/abort 等接口，供 Ymodem 回调使用。

- 从有效元数据确定 active_slot，target_slot 必须为另一槽；首次示例为 A 运行、B 接收。
- 检查首包长度后，先记录 RECEIVING，再擦除目标槽。
- 每个通过校验的新数据包按偏移写入，成功后再 ACK；ACK 不表示固件已激活。
- 处理 Flash 的 4 字节写入对齐：最后不足部分用 0xFF 补齐，逻辑长度和 CRC 仍按实际内容计算。
- 传输中错误、取消或超时停止写入并保留旧活动槽；错误记录写入本身失败时也不能改变启动选择。
- 全文件收齐后校验文件长度、镜像头、CRC32、地址与向量；协议 CRC16 与镜像 CRC32 分工不同，均保留。

验收：串口上传后目标槽内容与升级包逐字节一致，旧槽哈希不变；截断、越界、写入失败和坏镜像均不能激活。

### 6. 完成主备切换与新应用启动

建议状态流程：IDLE → RECEIVING → VERIFYING → READY → 提交新 active_slot 的 IDLE。失败记录 FAILED，active_slot 仍指向旧槽。READY 表示候选镜像已验证，只有提交新活动槽记录才表示升级生效。

- 校验新槽成功后再提交 active_slot；提交前中断选旧槽，提交完成后重启选新槽。
- 新启动路径读取元数据、校验活动镜像、复制到 APP_EXEC_BASE、复核复制内容，最后使用现有交接流程运行。
- 当前槽无效时保留 Bootloader 的重新升级入口；自动搜索旧版本、试运行确认、看门狗回退等完整策略归 Week 6。
- 连续执行 A→B、B→A 两次升级，确认槽角色没有写死。

验收：v1→v2→v3 连续升级成功，重启选择与参数区记录一致；提交前后的中断行为符合约定。

### 7. 建立 QEMU 中断与恢复验证

建议新增 codes/scripts/week5_session.py、send-week5.py、verify-week5.py；复用现有 QMP 基础，但二进制传输不能依赖文本提示符识别完成。

现有 Flash 后端是 SRAM NOR 模型，正常持久化依赖宿主快照。直接杀死 QEMU 并重新载入旧文件，会丢掉全部未快照写入，不能证明实际掉电恢复。

- 明确故障模型：在哪次擦除、编程或元数据提交操作之后/内部中断，哪些字节已落盘。
- 在受控故障点暂停 CPU，导出当时完整模拟 Flash 内容，再用该内容启动新进程；中间状态保存使用专用故障注入入口，不沿用“完整 UART 响应后才能快照”的普通会话假设。
- 补充部分正文、部分提交标记、部分擦除等撕裂状态；只在两次函数调用之间重启不足以覆盖写入中断。
- 每个用例保存故障点、快照、串口日志、活动槽、启动版本与预期结果。
- 区分“正常保存再启动”“升级过程故障注入”“实际硬件掉电”；本周只声称前两者的已验证范围。

最低测试矩阵：

| 用例组 | 预期 |
|---|---|
| 正常升级、连续反向槽升级 | 运行新版本，元数据和内容一致 |
| CRC16 错包、重复包、丢 ACK | 正确重传，不重复写入或增加偏移 |
| 超时、取消、断连、RX 溢出 | 退出升级，旧版本仍可启动 |
| 文件过大、长度不符、CRC32/向量错误 | 拒绝候选，不改变 active_slot |
| 目标槽擦除/写入中断 | 旧版本可启动，允许重新上传 |
| 镜像已验证但未提交 | 仍启动旧版本 |
| 元数据正文/提交标记写入中断 | 选择有效旧记录或完整新记录，无混合状态 |
| 完成提交后立即中断 | 重启运行新版本 |
| 参数区空白、单份损坏、双份损坏 | 初始化、使用剩余有效记录或进入恢复入口 |
| Flash 写入失败、状态保存失败 | 不宣告升级成功，不误切换 |
