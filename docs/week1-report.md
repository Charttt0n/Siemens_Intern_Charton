## 二 我对当前架构的理解

我把当前工程分成宿主机构建、目标机执行和调试观察三部分。这样能区分“生成了程序”“目标机执行了程序”和“我能解释执行过程”，避免只看到输出就认为启动链路已经理解完整。

```text
构建路径  CMake → Make → Arm GCC 和链接器 → ELF
运行路径  QEMU → 向量表 → Reset_Handler → main → 输出
观察路径  GDB → QEMU gdbstub → 寄存器和内存
```

启动汇编负责复制 `.data`、清零 `.bss` 并调用 C 入口；链接脚本决定这些内容放在哪里；C 示例检查 CPUID 和变量值；验证脚本负责建立可控初始状态、读取结果并判断退出码。GDB 只用于观察和注入测试条件，不是固件启动步骤。

本次复位观察得到 MSP 为 `0x20400000`、PC 为 `0xc4`，向量表中的复位入口为 `0xc5`。入口最低位表示 Thumb 状态，因此与函数指令地址差 1 是正常的。我也将初始栈指针与函数运行后的 SP 分开记录，避免把两个时刻的值误判为不一致。

我原先整理的内存表还需要一个边界说明：工程中的 CODE 区实际对应 QEMU 的 SRAM，不能因为链接脚本把它命名为 CODE，就认为已经具备 Flash 的擦写和掉电保存能力。这个区别会影响后续断电恢复测试的有效性。

## 三 测试如何补足正常启动的证据

### 为什么要污染内存

原来的示例会检查 `.bss` 变量是否为零，但模拟器可能恰好提供了零初值。这样即使没有正确清零，也可能得到相同观察结果。我因此把验证条件反过来设置：先明确写入错误值，再观察启动代码是否把它们恢复。

测试在 `Reset_Handler` 尚未执行时暂停，将 `.data` 运行区的 4 字节写成 `0xCC`，将 `.bss` 的 8 字节全部写成 `0xA5`，并在 `.bss` 末尾后放置 4 字节哨兵。到 `main` 第一条指令时再次检查，防止 C 程序后续赋值掩盖初始化问题。

实际结果：`.data` 恢复为 `0x12345678`，`.bss` 全部清零，哨兵仍为 `0x12345678`。这比单次正常启动多证明了一个关键事实：当前布局中的复制与清零代码确实执行了。

### 检查结果

| 检查项 | 操作或条件 | 实际结果 |
|---|---|---|
| 工具版本 | 检查六个工具和最低版本 | 通过 |
| 全新构建 | 新目录编译，运行和调试同一 ELF | text 368，data 4，bss 8 字节 |
| 正常启动 | 不注入故障 | PASS，退出码 0 |
| 污染后启动 | 污染数据区并检查末尾哨兵 | 恢复正确，退出码 0 |
| 破坏初始化变量 | main 入口改 initialized_data | FAIL，结果 0xdead，退出码 1 |
| 破坏零变量 | 独立实例中改 zero_data | FAIL，结果 0xdead，退出码 1 |

两个负向用例都把目标变量改为 `0xDEADBEEF`。此时固件退出 1 才符合预期，整个测试应判为通过。它们验证了示例能识别错误并走到失败路径，不代表已经具备 Bootloader 恢复能力。

本次还观察到单步 PC 从 `0x44` 前进到 `0x46`。日志保存了 GDB 命令、注入前后值、退出码，以及源码和 ELF 哈希。6 项检查全部通过，只代表这些明确条件通过；没有把它写成全系统或全部代码覆盖率 100%。

实验仍有限制：当前 `.data` 只有 4 字节、`.bss` 只有 8 字节；哨兵只覆盖一个末尾位置。不同段长度、空段和完整异常表还需要后续测试。

## 四 工业需求调研带来的设计思路

### 先区分不同层次的启动

阅读 Siemens 资料后，我将签名固件更新、Secure Boot 和 Startup OB 分开：更新文件在安装前验证；Secure Boot 在启动前验证待执行固件；Startup OB 则在 PLC 操作系统之上处理用户程序启动。这使我认识到，接收时验证通过还不够，启动时也需要重新判断即将执行的内容是否可信。[签名固件更新](https://docs.tia.siemens.cloud/r/simatic_s7_1500_et_200mp_manual_collection_enus_20/basic-information/automation-system/industrial-cybersecurity/secure-operation-of-cpus/signed-firmware-update-for-cpus)、[Secure Boot](https://docs.tia.siemens.cloud/r/simatic_s7_1500_et_200mp_manual_collection_enus_20/basic-information/automation-system/industrial-cybersecurity/secure-operation-of-cpus/secure-boot-for-cpus)、[Startup OBs](https://docs.tia.siemens.cloud/r/en-us/v20/functional-description-of-s7-1500-cpus-s7-1500/organization-blocks-s7-1500/description-of-all-types-of-organization-blocks-s7-1500/startup-obs-s7-1500)

S7 的装载存储器资料讨论 PLC 程序代码、数据块和配置，不能直接推出 CPU 固件分区。本项目只借鉴其存储职责划分，不把自己的 Cortex-M7 模型称为 S7 硬件仿真。Secure Boot 支持范围也需要按具体型号核实。

### 后续模块拆分草案

我倾向于先按故障责任拆分模块，让每个模块的输入、输出和失败行为能够单独检查。下表是后续方案，目前尚未实现。

| 模块 | 应承担的责任 | 我准备验证的问题 |
|---|---|---|
| 板级启动与应用交接 | 建立运行条件，交接栈、入口和中断状态 | 错误入口是否会被拒绝，应用是否继承了不该保留的状态 |
| 镜像验证 | 检查长度、完整性和签名 | 截断、超长或被篡改的镜像是否会被接受 |
| 存储抽象与升级记录 | 约束写入，保存可判定的升级状态 | 写入中断后能否识别哪条状态记录有效 |
| 传输与启动决策 | 接收候选数据，选择已确认或待试运行镜像 | 接收完成是否被误当作成功启动，失败时是否保留恢复入口 |

我认为双镜像设计最需要想清楚的是“何时承认新版本有效”。把文件写完就切换过早，因为它可能验证失败，也可能能通过校验但无法正常启动。因此，初步方案是保留已确认镜像，候选镜像经过验证后试运行，由应用确认成功，再提交状态。后续要分别测试写入中断和试运行失败，不能只测成功升级一次。

IEC 62443 的学习目前停留在公开概览和开发思路。我能落实到当前工作的，是让需求、实现、测试证据和限制一一对应；不会把采用 SHA-256 或 RSA 写成已经满足标准或通过认证。[IEC 标准概览](https://syc-se.iec.ch/deliveries/cybersecurity-guidelines/security-standards-and-best-practices/iec-62443/)
